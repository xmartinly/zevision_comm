## Project overview

Zevision ("IMC300通讯测试") is a WPF desktop app that talks to an INFICON IMC300 thickness monitor over RS232 or TCP (Ethernet port 2101) using the Zevision protocol (`docs/Zervison_Protocol.md`). The UI uses Material Design. The UI shell exists: `App.OnStartup` (no `StartupUri`) creates `Views/MainWindow` with `MainViewModel` as its `DataContext`. The left panel holds the connection settings (RS232 or TCP), protocol options, connect/disconnect and the instrument-configuration buttons; the right panel holds the log display and command input. Everything has been run against a real IMC300 (firmware 1.8.11).

- Topology (user, 2026-10-23: "客户的软件, 连接到库文件和虚拟的串口,虚拟串口通过TCP和仪器通讯"): customer software (XTC/3 over serial) → COM1 ⇄ virtual pair ⇄ COM2 → bridge libraries → TCP 2101 (Zevision) → IMC300. The virtual pair driver (Eltima VSPD 6.9 on this PC) only passes bytes between the two ports; the bridge makes the TCP connection. Hosting (user decision: both): the standalone program, or in-process in a .NET customer application through `Xtc3BridgeHost.Start(settings, log)` (`Zevision.Bridge.Hosting`: loads `Texts.json` if `TextCatalog` is empty, `FileErrorLog` in `logFolder`, `ZevisionDeviceService`, `JsonFileBridgeStateStore`; changes `Lang` only when `language` is `en`/`zh`, because `Lang` is process-global and the tests assume Chinese). `Xtc3BridgeSettings` = `xtc3bridge.settings.json` (hostPort, hostBaudRate, device = IP or `COMx[:baud]`, createShadowObjects, shadowBase hex, stateFile/logFolder relative to the settings file, version, language); the console's `init` writes it and running without arguments uses it. - `Zevision.Xtc3` (references only the framework; `LibraryBoundaryTests` checks it and that both bridge libraries have no Chinese string literals): `Xtc3PacketDecoder` (2-byte LE length, checksum without length, 3 s inter-character timeout → discarded bytes, length 0/>57800 → packet error L and the rest of the read is dropped), `Xtc3MessageParser` (syntax table in `Xtc3Syntax`; illegal IDs → C and the parameters are skipped by syntax, UF/UG values are always 4 bytes; unknown group/sub-group and UN/UI/UO/UT/UP/UB take the rest of the message as one `A`; QB/QN/QI/QO/QT/QP → A with known length; missing bytes → packet error F; >100 commands → M), `Xtc3Command` (factories), `Xtc3Value` (Byte/Word/Integer/Float/String/Bytes, LE), `Xtc3Parameters` (Film 0–37, General 0–15 with ranges and XTC display decimals; `IsValid` rounds floats to those decimals), `Xtc3ResponseEncoder` (CCB 0 + Timer + ACK/values or error code; packet error = CCB 0x80 + one code; no trailing packet error code on success; responses over 57800 → O then P), `Xtc3HostCodec` (host side encode/decode for tests and the console client), `Xtc3State`/`Xtc3StatusMessages` (S33 bits re-sequenced to one bit per item because docs/XTC3.md has duplicate values).
- `Zevision.Bridge` (references Communication, Commands, Core, Xtc3; not Storage): `Xtc3Bridge` (public: `StartAsync`/`StopAsync`, `ProcessPacketAsync`, `CreateShadowObjectsAsync`, `Log`/`HostExchange` events; device loop = connect → handshake → `PrepareAsync` → sample every tick boundary until `ConnectionLost` or `SampleMissLimit` misses → reconnect with `ReconnectPolicy`; host loop = `IDeviceTransport` (SerialPortTransport) + decoder, reopens after UG14 at the new baud, waits `HostRetryInterval` after a port error), internal `BridgeEngine` (partial files: core/exchange, `.Parameters` QF/UF/QG/UG, `.Status` sampler + S commands, `.Remote` R commands), `ShadowFilm`/`ShadowObjects` (Film n ↔ `M/F/L/P02` + (0xB0 + n), names `XTC Film n`; check = name and structure (`F02`, `F03FE`=2, `F05FE`=1, `F07FE`=1, `L02FE`=1, `L020101`, `L020106FE`=1, `P0207FE`=1, `P020701`); create = recipe of the missing objects through `RestorePlanner` + `ExecuteRestoreAsync`, existing objects are not written), `FilmMap` (item paths and device decimals from the real help table), `DeviceStates` (C09 text → XTC state by name), `BridgeLocalState` + `IBridgeStateStore` (`JsonFileBridgeStateStore`, `MemoryBridgeStateStore`; `BaudRate` null = use the options' host baud).
- Device access goes through `IDeviceService.SendAsync` only (no priority: host packets are processed one at a time, so they wait at most one sample frame). Writes are `U<id>:<v>;Q<id>` in one frame per item (10 items per frame for 255), read back with tolerance = half of the XTC display precision; numbers are written with the device's decimals (density 3, power 2, PID 3, rate 3, ramp start thickness 4). Device `-B` → B, `-F` → F, others/transport → E; for R commands `-A` → A.

## Languages (Chinese / English)

- `Zevision.Core/Localization/Lang` picks the language once in `App.OnStartup`, before anything else is created (the error-log session header uses it).
  - Rule: Chinese if the Windows display language is Chinese or the region format is China (CN); English otherwise.
  - `settings.json` `language` (`auto`/`zh`/`en`) overrides it. `MainViewModel` keeps that value when saving.
  - Switching at runtime is a restart, not live re-translation (texts and `x:Static` XAML are fixed at load).
    - The "EN"/"中" button (`SwitchLanguageCommand`) is in the data-display header and is disabled while a configuration operation runs.
    - It confirms, sets the target language and raises `RestartRequested`.
    - `App.OnRestartRequested` then:
      1. Saves preferences, so the new process reads the new language.
      2. Disposes the single-instance mutex; otherwise the new process would just activate this window and exit.
      3. Starts the exe and shuts down. If the start fails, it re-acquires the mutex and keeps running.
- UI text (app project) is written as pairs at the call site: `Lang.T("中文", "English")`. There are no resx files, because the build has no VS custom tool to generate designer code.

## Architecture

Data flow: `MainViewModel` → `IDeviceService` (`ZevisionDeviceService`, Core adapter) → `ZevisionClient` (library) → `IDeviceTransport` (`SerialPortTransport` or `TcpTransport`). Received bytes go through `ZevisionFrameDecoder`, then `ZevisionResponseParser`.

Layers (0.10.0 refactor; behavior, texts and file formats unchanged):

| Layer | Assembly | Interfaces it offers / uses |
|---|---|---|
| UI | `Zevision.exe` (Views, ViewModels, App) | uses Core interfaces only; `App` (composition root) creates the Storage implementations |
| Business logic | `Zevision.Core.dll` | offers `IDeviceService`, `IInstrumentConfigReader/Writer/Service`, `RecipeEditSession`, pure rules (`RecipeRules`, `RestorePlanner`, `ObjectTypes`, `DeviceIds`, `ParameterValue`, `ManualCommandPolicy`); defines `IRecipeStore`, `IPreferencesStore`, `IErrorLog`, `ICommunicationRecorder(Factory)` |
| Data storage | `Zevision.Storage.dll` | implements them: `RecipeFileStore` (`RecipeFile` format + MD5), `JsonFilePreferencesStore`, `FileErrorLog`, `CommunicationLogFiles` → `CommunicationLogWriter`, `AppFolders`, `TextFile` (reads `Texts.json` for `TextCatalog`) |
| Protocol | `Zevision.Commands.dll`, protocol part of `Zevision.Communication.dll` | `ZevisionCommandSet`, `ZevisionClient`, codec/decoder/parser |
| Hardware communication | `Zevision.Communication.dll` | `IDeviceTransport` (`SerialPortTransport`, `TcpTransport`) |

- Pure functions (rules, planner, ID helpers) are static and have no interface on purpose; interfaces exist only where an implementation is swapped (tests, storage).
- `LibraryBoundaryTests` guards the layers: referenced assemblies of each library (Core: framework + the two libraries, no WPF/Storage; Storage: framework + Core), no file types in Core's metadata, no Chinese literals in Communication/Core/Storage, and no `Zevision.Storage` in `ViewModels/` or `Views/` sources (all subfolders; the test also checks it found the files).
- Not done on purpose (plan items dropped during the refactor): a `ConnectionService` (the recorder must stay open until the "连接中断" line is logged by the view model) and a `ConfigBackupService` (save/restore in `ConfigOperationsViewModel` only sequences Core calls with dialogs in between; a wrapper would add code without decoupling).

Libraries (split 2026-10-16, user request: "只做指令生成, 通讯数据传输/解析", no logging, English output, communication parameters passed at construction):
- `ZevisionClient(ConnectionOptions options[, transportFactory])`: one instance per device and options; `ConnectAsync(ct)`, `DisconnectAsync()`, `SendAsync(command[, minimumResponseTimeout], ct)`; reconnect with the same options is allowed; after `Dispose` `ConnectAsync` throws `ObjectDisposedException`. It holds what used to be in `ZevisionDeviceService` (session, read loop, echo correlation, idle timeout, filler, partial-frame flush).
- Results are `ZevisionResult`/`ZevisionResult<T>` with `ZevisionError` (`Kind`: AlreadyConnected, ConnectFailed, NotConnected, InvalidCommand, SendFailed, Timeout, Disconnected, InvalidFrame, UnparseableResponse; English `Message`; data: `Exception`, `Endpoint`, `Timeout`, `ReceivedIncompleteData`, `FrameError`, `DataLength`). The application's `Zevision.Core/Result` is separate (localized messages).
- No logging in the libraries: an unexpected read-loop exception ends the session and is passed in `ConnectionLost`; an exception from an event handler is passed in the `HandlerFailed` event (exceptions from `HandlerFailed` handlers are ignored). The session's `CancellationTokenSource` is deliberately not disposed (no timer or linked tokens; a lost connection and a disconnect can end the session on different threads, and cancelling a disposed source throws).
- `TcpTransport` throws `TimeoutException` (not `IOException`) for the 5 s connect timeout, so the app can show its own text.
- `ZevisionDeviceService` (Core, `Zevision.Core/Devices`) implements `IDeviceService` on top: it creates a new `ZevisionClient` per `ConnectAsync` (detaching and disposing the previous one), forwards the events with itself as sender (`Retrying` only for visible sends), maps errors through `CommunicationText.Describe`, and writes non-I/O `ConnectionLost` exceptions (reason `ReadFailed` only) and `HandlerFailed` to `IErrorLog` (same entries as before the split). It also implements `HandshakeAsync` (below) through the internal `IHandshakeLink`.

Session layer (1.1.0; user request 2026-10-19, decisions: handshake failure disconnects but handshake can be switched off, auto-reconnect off by default, heartbeat on RS232 and TCP):
- Handshake (`IDeviceService.HandshakeAsync(preferred, ct)` → `Result<DeviceIdentity>`; algorithm in internal `Core/Devices/DeviceHandshake`): send `H01` in the preferred format without retry; if the reply is not `H01+…`, wait `DeviceHandshake.Settle` (300 ms; the device answers wrong-format input within about 230 ms), detect the device's format from all bytes received meanwhile (`FrameFormatDetector.Detect`: tries LC, L, C, P decoders, first that yields only valid, parseable frames wins; leading garbage ignored), switch (`ZevisionClient.ChangeFrameOptionsAsync`) and resend; otherwise try the remaining formats (max 4 attempts). No bytes at all on the first attempt → fail at once (the device always answers). Then one frame `QG03;QG06;QG1304;QG1305` (TCP: G1407/G1408): no model → fail; G06 (system serial number, `DeviceIdentity.SerialNumber`, null when not answered; names the communication data file) never fails or warns; model ≠ `DeviceIdentity.ExpectedModel` (IMC300) or reported settings ≠ the working format → `Warnings` (localized). While handshaking the adapter forwards no `FrameSent`/`FrameReceived` and captures the raw bytes (max 4 KB). Real device: RS232 LC→P detected in 463 ms, TCP P→LC in 378 ms.
- `FrameSettings` (Core/Devices; replaces `FramingCheck.SettingIds`): `Ids(endpoint)` and `AfterUpdates(endpoint, current, commands, responses)` = the new frame after an accepted `UG1304/1305/1407/1408` (null if unchanged). The device answers that `U` in the old format and only accepts the new one from the next frame (measured).
- Retries (library, inside the send lock): `RetryPolicy` (internal) retries only transmission failures (Timeout, InvalidFrame, UnparseableResponse, device codes C/L/T) and only frames whose every command starts with Q/S/U/H/E/? (A/D/R change state when repeated; a timeout does not prove the device did nothing). A/B/D/F are not retried. The app uses 2 retries when handshake is on (`ConnectionSettingsViewModel.HandshakeRetryCount`), 0 when off; each retry is logged as an info line (`CommunicationText.DescribeRetry`).
- Heartbeat (library, `HeartbeatLoopAsync`, one task per session): when the connection has been idle (no send/receive) for the interval and the send lock is free (`PriorityLock.TryEnter`), send `H01` silently (no events; its reply is claimed silently). Any answer counts; Timeout/SendFailed count as misses, the next one is sent immediately; `HeartbeatMissLimit` misses → `EndSession` + `ConnectionLost(Reason = HeartbeatTimeout, TimeoutException)`. `DisconnectAsync` awaits it. App: 5 s / 3 when handshake is on (`HandshakeHeartbeatInterval`).
- Send lock: `PriorityLock` (internal, replaces the `SemaphoreSlim`): one holder, waiters ordered by `SendPriority` then FIFO, cancellation removes a waiter. Nothing in the app uses High yet (no polling, no stop commands).
- `ConnectionLifecycle` (ViewModels/Main, UI thread only): `ConnectionState` Disconnected → Connecting → Handshaking → Connected; on `ConnectionLost` while Connected: logs "连接中断: …", closes the recorder, then either Disconnected or Reconnecting (auto-reconnect: `ReconnectPolicy.DelayBefore` 1, 2, 4 … 60 s via the injectable `Delay`, then open + handshake with `CreateOptions()`; reconnect failures are Info lines, not errors). Disconnect stops a reconnect loop ("已停止自动重连。"). `OnFrameSettingsChangedAsync` re-handshakes after an accepted frame-setting write (handshake off: info hint only; failure: error + disconnect). Interrupted config operations and repeat sending are not resumed. It owns the communication-data recorder (opened per successful connection).
- `MainViewModel` exposes `ConnectionState`, `IsConnected` (= Connected), `IsDisconnected` (panel enable), `IsConnecting` (status dot), `HasConnection`, `StatusText` (connecting/handshaking/"连接中断,x 秒后第 n 次重连 …"); Disconnect is enabled while reconnecting. With handshake on, a manual reply containing `-F` triggers a visible `QC09` query and an info line with the state; `InstrumentConfigReader.SendForResponseAsync` appends `Texts.CurrentDeviceState` to F rejections (never switches the device state).
- Switches "连接时握手" (`IsHandshakeEnabled`, default on) and "自动重连" (`IsAutoReconnectEnabled`, default off) are shared by RS232/TCP, stored as `handshakeEnabled`/`autoReconnect`. Handshake off = 1.0 behavior exactly (raw channel, switches decide the frame, no retry/heartbeat/F query). Detected frames update the selected type's switches (`ApplyFrame`) and are saved.
- Tests: `ClientSessionTests` (retry rules, heartbeat, priority lock, frame change), `FrameFormatTests` (detector with the 2026-10-19 raw replies, `FrameSettings`, `ReconnectPolicy`), `HandshakeTests` (through `ZevisionDeviceService` against `Fakes/SimulatedImc300`, which reproduces the measured wrong-format answers and the old-format reply to frame-setting writes), `ConnectionLifecycleTests` (MainViewModel with `FakeDeviceService` under an inline `SynchronizationContext`, so every await completes synchronously). - Serial line format is fixed at 8N1. `SerialSettings` takes only the port name and baud rate, because the IMC300 exposes only the baud rate (G1303). The UI has no data-bits, parity or stop-bits options.
- Manual input supports multiple commands in one frame (`QG01;QG1304;QG1305`).
  - `ManualCommandPolicy.Split` splits on `;`, full-width `；` and line breaks (the input box is multi-line: Enter sends, Shift+Enter inserts a line break, handled in `MainWindow.OnCommandInputKeyDown` because a `KeyBinding` on Enter would compete with `AcceptsReturn`), trims, and drops empty segments. The segments are re-joined with `;` and sent as one frame.

  - Display format `DisplayFormat` (`ViewModels/Display/DisplayFormat`: Ascii default = the original output, Hex 32 bytes/line, Binary 16 bytes/line, whole frame byte by byte). Stored in a `volatile` field because `OnFrameSent`/`OnFrameReceived` read it on the background thread; it applies to frames formatted after the change.
  - Sending keeps the input text (user request; it used to be cleared). Before sending, `ManualCommandPolicy.ToUpperCommands` upper-cases the command part of each command (up to the first `:`; data after it, up to `;`/`；`/line break, is untouched because it may be a name) and the box shows the converted text. The device answers lowercase commands with `-A`. Repeat send uses the text captured at the click. The last sent input text (after the upper-case conversion, line breaks kept) is saved on exit as `lastCommand` and put into the input box on start (user request 2026-10-21: "保存上次发送的指令文本到输入框"); `MainViewModel._lastSentCommand` is set only by the Send button/Enter (quick commands do not count), so edits that were not sent are not saved and a session without sending keeps the previous value.
  - Repeat send: `RunAsync(exchange, canContinue)` sends, waits `RepeatInterval` (100–2000 ms, list only) after each reply or timeout, and repeats until `Stop` (Stop button replaces Send), unchecking, disconnect or connection lost. The exchange in progress is never cancelled (cancelling would leave a stale reply); only the delay is. Only the Send button repeats, not quick commands.

  - All three are stored in `settings.json` (`displayFormat`, `repeatSend`, `repeatIntervalMs`), as is the last sent command (`lastCommand`).
- Closing while connected or connecting (`MainViewModel.HasConnection`): `MainWindow.OnClosing` cancels the first close and awaits `MainViewModel.CloseConnectionAsync`, then closes again. A second close request during that time is ignored (`_closing`).
  - `CloseConnectionAsync` waits for a pending connect (otherwise the communication data file opened on success would never be closed), then `Config.CancelAndWaitAsync()` (cancels the running save/restore/edit and waits for the whole command; meanwhile no dialogs or editor window are shown, results go to the log only), then disconnects (stops repeating, finishes and closes the communication data file).

- `Zevision.Communication/` and `Zevision.Commands/` (libraries, no WPF dependency):

  - `ZevisionCommandSet` (+ `CommandDefinition`) is the command set and the single source for every command's pattern, actions, Chinese name, unit, range and options. It is built from the protocol doc §4 and the U-command xlsx, and real-device deviations are commented in the table.
    - Patterns use `**` for one 2-hex level. The first level is the object number (material in `M**03`, film in `F**02`, process in `P02**01`); later levels are sub-list numbers (`F**03**01`).
    - API:
      - `TryGetGroup("M0103", out g)` → `CommandGroup.M`.
      - `GetCommands(CommandGroup)` lists a group's commands.
      - `Find(id)` picks the most specific pattern, so `MFE` resolves to the count and `M03` to `M**` (add).

      - `ZevisionCommandSet.Query(id)`, `Update(id, value)` and `Add(id)`, or `Build(action, id, value)`, are used for quick commands, `QueryAsync`/`QueryValueAsync`, `RestoreWrite.Command` and the planner's `A…` creates.

- `ZevisionClient` (library; the app reaches it through `Zevision.Core/Devices/ZevisionDeviceService`):
  - One background read loop per connection (`Session`).
  - Slow replies use a minimum idle timeout. `SendAsync(command, minimumResponseTimeout, ct)` waits at least that long; the longer of the connection timeout and the minimum wins.
    - `InstrumentConfigReader.SlowReplyTimeout` (2 s) is used for `?` and for batched `QueryAsync` frames.
    - Real captures show `?` takes about 380 ms to its first byte and about 350 ms between 57000-byte packets, so a 500 ms user setting was too tight.
    - The batch-query processing time is not yet measured.
  - `SendAsync` is serialized by the `PriorityLock` (was a `SemaphoreSlim`; see "Session layer (1.1.0)"). It sets a `TaskCompletionSource` as the pending request, writes the frame, and waits. `ResponseTimeout` is an idle timeout, measured from the send or the last received byte, so large replies (for example `?` help) can take seconds to arrive at 115200 bps without timing out. Keep it idle-based.
  - `ConnectionOptions` (endpoint, frame options, response timeout) is passed to the `ZevisionClient` constructor; there is no mutable configuration. The app's `IDeviceService.ConnectAsync(options)` keeps its signature and creates a client per connection.
  - Echo correlation: the pending request stores `ZevisionResponseParser.EchoOf(command)`. A frame completes it only if `IsReplyTo(frame, echo)`: same echo (case-insensitive), or undecidable (invalid frame, unparseable, echo-less `-C`). Anything else is a stale reply (for example the tail of a cancelled `?`) and is shown as unsolicited instead of being taken as the answer.
  - The read loop has a catch-all: an unexpected exception ends the session with `ConnectionLost` (carrying the exception) instead of killing the process. Event subscribers are invoked through `Raise`, which reports subscriber exceptions through `HandlerFailed` so they cannot break the loop. The app adapter logs both to error.txt.
  - Events (`FrameSent`, `FrameReceived`, `ConnectionLost`) fire on background threads.
  - `ConnectionLost` fires only on unexpected read failure, never on `DisconnectAsync`.
- `.NET Framework` `SerialPort.BaseStream.ReadAsync` ignores its `CancellationToken`. A pending read ends only when the port is closed, so `EndSession` cancels first and then closes the transport. The read loop treats any exception after cancellation as a normal shutdown.
  - Consequence: disconnecting or exiting while connected always produces a **handled** first-chance `IOException` (ERROR_OPERATION_ABORTED) in the VS Output window. This is expected; do not "fix" it by switching to `DataReceived`, which would lose USB-unplug detection, since that relies on the read throwing.
  - `SerialPortTransport.Close` swallows IOException/UnauthorizedAccess/InvalidOperation from `Close()`/`Dispose()`, which can happen when the adapter was already unplugged.
  - `App.OnExit` runs each cleanup step (save preferences, dispose VM, dispose service) independently through `RunOnExit`, which logs failures to error.txt.

Final results only, so a command that succeeds after a retry is not counted.   - Background refresh (user requests 2026-10-21: "当程序不在前台时降低通讯数据显示刷新率", and 2026-10-22: "当程序不在前台时, 将数据刷新频率调整为保存数据时统一显示"): `LogViewModel.IsInBackground` is set by `MainWindow` code-behind from `Application.Activated`/`Deactivated` (application level, so the editor window or a message box in front still counts as foreground) or `WindowState == Minimized`. ## Process editor (工艺编辑)

User request 2026-10-22. The user writes materials and processes locally. "Save" stores them and then uploads the selected process.

- Purpose (user, 2026-10-22): "为了简化实机流程使之更符合操作习惯", i.e. to simplify setting up processes on the instrument the way operators work.
- Decisions (user): write everything first; "保存" saves locally and "上传" saves and uploads (2026-10-23; until then "保存" did both); reuse existing materials/films/layers and create new ones only when parameters differ (user request 2026-10-22, replacing the first "always new" decision); new layers are named `<material>-<process>-<step number>` (user request 2026-10-23: "新建layer时,使用材料名-工艺名-步骤号来命名"; until then `L_<material name>`); materials have a Chinese name (local only); a process can use several materials (one material per step, no co-deposition); the later film parameters (max power, crystal position, pre/post step values, delay option, rate ramps, auto start next) are editable; density/Z can be typed or picked from the material library (the user supplied it as `docs\materials.json`: the material table of Annex A of the IMC300 operating manual, 253 materials); the active process (`P01`) is never set.
- Mapping (`Zevision.Core/Design/DesignBuilder`, pure). Each material used corresponds to one material and one film with the same name (reused or new):
  - Material: `M**01/03/04/07`.
  - Film: `F**01`; `F**02` = the material's decimal number; pre conditions `F**03nn01..03`; delay option `F**0401`, and only when it is not 0 (`MaterialDesign.HasDelaySettings`) the delay settings `F**0402..06` (control delay time, shutter delay accuracy, shutter delay timeout, transfer sensor 0 = none, transfer tooling; a non-zero transfer sensor must exist on the device, checked in `ValidateUpload`); post conditions `F**05nn01..03`; sensor list item 1 `F**070101/02`; source, crucible, P, I, D, max power, max power option `F**0901..07`.
  - Each step corresponds to one layer: a new layer is named `<material>-<process>-<step number>` (`LayerName(material, process, stepNumber)`, `LayerNameSeparator`, e.g. `Al-AR-1`; a layer shared by identical steps of one process takes the first step's number), film entry 1 `L**020101/02/03` (film number, rate, thickness), ramps `L**020106kk01..03`.
  - Names (material, process and generated layer names) have at most `DesignRules.MaxNameLength` = 30 characters (real device 2026-10-23: names are stored up to 31 characters, longer ones are truncated, and the `?` VALUE column shows only the first 30; reuse and delete compare names read with `?`). `Validate` checks the names (`DesignNameTooLong`) and the generated layer name of each process's first occurrence of a step (`DesignLayerNameTooLong`); the name boxes have `MaxLength="30"`. A 32-character name made the upload fail at verification (31 read back).
  - Reuse (`Reusable`):
    - Candidates: the first existing object of the group, by number, whose generated fields all match the snapshot (`ParameterValue.AreEquivalent`: names as strings, numbers and times by value) and whose sub-list counts match (`…FE`).
    - Material: name, density, Z, tooling.
    - Film: searched only when the material was reused (a new material has no films). All film fields including `F**02`, same pre/post counts, exactly 1 sensor.
    - Layer: searched only when the film was reused. Exactly 1 film entry with that film, rate, thickness, same ramp count and values; the name is not compared (`StepFields(…, layerName: null, …)`), because a layer with these values may come from another process or step. A reused layer's `DesignObject.Name` is its device name.
    - Reused objects get no entries (`DesignObject.IsNew = false`). A changed step of a re-uploaded process creates a new layer with the same name (e.g. a second `Al-P1-1`).
    - Within one upload, steps with the same material/rate/thickness/ramps (`SameStep`) share one layer.
    - The process is always new.
    - The real capture already has `M10 Al` (2.700/1.080/100.00), so the capture-based test reuses it.
  - The process gets `P02**01` (name), `P02**02 = 1`, `P02**04` (auto start next) and `P02**07nn` (the layer numbers in step order).
  - Numbers are the first free ones on the device (`ObjectType.NextFreeId` over the snapshot's objects).
  - Field numbers are named constants. Validation (`DesignRules`) runs the same field generators against sample IDs (`M01`, `F01`, `L01`, `P0201`) and `ParameterValue.Validate`, so ranges, options and protocol characters come from the command set. Labels come from `LabelFor` (list items) or `Label`.
  - `ValidateUpload` adds the device checks: sensor `N`/source `S` exist, and `CrucibleRule.Check` with the film's planned source.
  - Material names must be unique, case-insensitive; process names too.
- Upload = the restore pipeline: `DesignBuilder.Build` → partial `InstrumentRecipe` (header from the snapshot) → `RestorePlanner.Plan` → `ExecuteRestoreAsync`.

## Serial (RS232) rules

- The `SerialPort.DataReceived` event runs on a thread-pool thread. Never touch UI objects from it. Marshal to the UI with `Dispatcher` only when UI state must change.
- Do not block on reads. Use `SerialPort.BaseStream.ReadAsync` with a `CancellationToken`, or a single dedicated reader task that feeds a byte buffer.
- Parse frames from a byte stream, not from individual reads. A frame starts at `{` and ends at `}`. One read can contain part of a frame or several frames, so accumulate bytes and handle both cases.
- Use one outstanding request at a time (for example, a `SemaphoreSlim` around send-and-await-response) unless the protocol says otherwise. Give every request a timeout. The protocol's `T` error code is a 200 ms inter-character timeout, which is a separate concern from the request timeout.
- Check `G1304` (checksum) and `G1305` (length) on the device before assuming either is enabled. The parser must handle both states.
- Parse numeric responses with `CultureInfo.InvariantCulture`. Decimal separators from the device are `.`, and the PC locale may not match.
- Use ASCII for protocol bytes. Do not encode command strings with the system code page.
- Enumerate ports with `SerialPort.GetPortNames()`. Do not hard-code `COMx`.
- Handle `IOException` and `UnauthorizedAccessException` on open, read, and write (the device may be unplugged or the port in use). Close and dispose the port on exit.
- Treat `-` responses and error codes as typed results (an enum, not a string) so the caller can branch on them.

## Async and threading

- Use `async`/`await` for all I/O. Forward `CancellationToken` through every async call.
- Never use `.Result`, `.Wait()`, or `.GetAwaiter().GetResult()` on UI or serial paths. These can deadlock the WPF dispatcher.
- Use `ConfigureAwait(false)` in the libraries (including `Zevision.Core` and `Zevision.Storage`). Do not use it in view models or code that updates the UI.
- `async void` is allowed only for event handlers and `ICommand` implementations, and those must catch and handle their own exceptions.
- Update `ObservableCollection` and other bound state on the UI thread.

## Error handling

- Use exceptions for transport failures (port missing, unplugged, write failed). Catch them at the service boundary, not in view models.
- Use a Result type for expected protocol outcomes (device returned `-`, `B` illegal argument, timeout). On C# 8, a small `readonly struct Result<T>` is enough.
- Do not catch bare `Exception` without rethrowing or logging it.

## Code style and quality

- Nullable reference types on. XML documentation on public types and members in the libraries, including Core and Storage (they generate `.xml` doc files, so a missing `<see cref>` target fails the Release build).
- Keep a single source of truth for protocol constants (command IDs, error codes). Do not repeat magic strings across files.
- Do not edit generated files (`*.Designer.cs`, `*.g.cs`, anything under `obj/`).
- New protocol logic (framing, checksum, parsing) needs unit tests. xUnit runs on net472. Test with a fake serial port, not real hardware.

## Protocol reference (docs/Zervison_Protocol.md)

The doc is the authoritative source for the serial layer. Key points:

- Transport: RS232, default 115200 bps (`G1303`), protocol type 0 = Zevision (`G1301`).
- Framing: `{` start, then command or response data, then `}` stop. With `G1305` (length) enabled, a 2-byte big-endian length follows the start character. With `G1304` (checksum) enabled, a 1-byte checksum (sum of command data modulo 256, excluding framing bytes) precedes the stop character.
- Commands: an action letter (`U` update, `Q` query, `A`/`D` add/delete, `S` status, `R` remote, `E` echo, `H` hello, `?` help), a group letter, then 2-hex-digit IDs (`00`–`FF`), with data after `:`. Several commands can share a frame, separated by `;`.
- Responses: echo of the command, then `+` (ok) or `-` (error), then an error code (`A` illegal command, `B` illegal argument, `C` checksum, `D` bad format, `F` bad state, `L` length, `T` timeout) or `:` followed by data for queries.
- Materials: the doc says IDs run from `01` to `C8` (1–200), but the device has materials up to `FA` (250); see the real-device findings. IDs are substituted for `**` in `M**` commands and need not be contiguous. The list starts empty; materials are added with `M00` (action `A`), then updated with their fields.
- The doc is for communication testing only. The instrument must not be installed in evaporation coating tools.
- Real-device findings on IMC300 firmware 1.8.11, with checksum and length enabled:
  - `H01` → `{<00>(H01+:Zevision IMC300 1.8.11.202606101229<C5>}`. This confirms the length field is big-endian and the checksum is a sum modulo 256.
  - Large replies are split into multiple packets. This is not in the protocol doc:
    - Format: `{`[len]data[cs]`>` `<`[len]data[cs]`>` … `<`[len]data[cs]`}`.
    - `>` means another packet follows, `<` starts a continuation packet, and `}` ends the message.
    - Each packet is at most 57000 bytes and has its own length and checksum, both covering only that packet's data.
  - Observed for `?`: 3 packets of 56931, 56957 and 2604 bytes (about 116 KB in total, about 10 s at 115200 bps). The stream ended with `<C8>>}`, so the last packet may also end with `>` before the final `}`; the decoder accepts both endings.
